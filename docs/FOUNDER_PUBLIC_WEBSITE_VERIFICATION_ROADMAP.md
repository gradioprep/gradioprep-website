## 2. Preview first; custom domain postponed, not abandoned
- **Preview is the verification destination NOW.** Prefer the existing Cloudflare Worker Preview mechanism and a stable, non-production preview identifier or explicitly versioned Preview URL. Never reuse an older preview as evidence for a newer commit; verify and share the live URL, build SHA, HTTPS and displayed functionality. Automatically publish or update the safe Preview after full exact-head CI for a feature batch; do not depend on manual DNS operations.
- **Known workflow issue:** `.github/workflows/phase1b-verification.yml` runs on branch `push`, but its Preview deployment and PR update are guarded by `github.event_name == 'pull_request'`; this path cannot deploy from that push-triggered job. In the NEXT substantial application/CI change, fix this trigger/logic with least-privilege Cloudflare credentials and positive isolation checks. A docs-only update does not fix the workflow. The previous app/test HEAD `0a401268df2b4950e1088bfa5a1e63023abfac12` failed Actions #43818955574 on a SQL `AS $` vs `AS $$` syntax error; repair that first.
- **Public visibility is not security:** even an unknown URL can be discovered. Restrict unfinished Owner/tester workflows with real authentication and roles; ideally restrict the test site if supported at $0, without accidentally making it impossible for the Founder to verify. A noindex rule is optional defence-in-depth, not access control. Expose only approved public-safe pages and published learner content. Never leak synthetic secrets/local env files, private packs or actual learner records.
- **$0 test backend:** use only services with confirmed free limits and an isolated Auth/PostgreSQL/RLS implementation compatible with the existing schema and Worker routes. Verify read/write, authenticated roles, denial paths, backups/rollback and account separation with synthetic data. Do not silently substitute Cloudflare D1 for PostgreSQL/Supabase or replace security policies. If $0 connected testing cannot be made secure/feasible, state the concrete limitation; keep delivering Preview frontend and local end-to-end tests instead of blocking all development.
- **Deferred domain:** on 16 Nov the connected Cloudflare account showed an existing `gradioprep-website` Worker but no `gradioprep.com` zone or Worker custom-domain mapping. An attempt to create the zone returned HTTP 403 for `com.cloudflare.api.account.zone.create`; no DNS changes happened. This permission issue **does not block Preview or feature implementation**. Only when the Founder chooses, create the Cloudflare Free zone through the authorised account, preserve registrar DNS/MX/TXT/email records before any nameserver switch, connect the appropriate verified Worker build and confirm TLS/redirect/hostname routing. Do not require Founder DNS work, extra approval for each Preview, or changes to production until requested.
