## 4. CI and release rule
1. Implement one coherent user-facing feature end-to-end; do lightweight syntax, type, targeted SQL and focused browser checks DURING development, before each commit when possible.
2. Use one complete GitHub-hosted CI pipeline on the consolidated application/test HEAD as the release gate: RLS/security, builds, critical browser tests, synthetic backup/restore. Fix failures on the same feature; stop meaningless commit-and-cancel chains.
3. After full green CI and isolation checks, deploy the changed build to the EXISTING approved test website/domain, then perform real browser acceptance. Existing `.github/workflows/phase1b-verification.yml` is `push`-triggered but preview-upload steps are gated on `github.event_name == 'pull_request'`; therefore it **does not deploy a Preview on that push path**. Correct the deployment trigger in an authorised app/CI change with scoped secrets, not in a docs-only commit; do not assert public verification from green CI alone.
4. Separate public shell from backend-connected test; do not deploy local synthetic Supabase keys, private teacher files, real learner data or unrestricted staging APIs.
5. Documentation changes go in a separate docs-only commit and should not trigger full application CI. No production release or PR merge without the separate required explicit approvals.
