## 1. Purpose and controlling decisions

This plan translates the revised six-unit public-framework-informed Year 1 guide into content architecture, metadata, review controls and a possible application implementation sequence.

It does not:
- claim IB endorsement or current official objective mapping;
- mark any unit Published;
- create or replace lesson content;
- modify the app's current catalogue or route data;
- author/adapt Unit 1 before founder approval;
- advance the next curriculum checkpoint.

The existing preview “How writers shape meaning” is a candidate for Unit 1 and must be reconciled, not duplicated, once the revised guide is approved.

## 4. Required source and framework metadata

Each curriculum guide, unit, lesson, task and rubric must keep these separate fields. Do not flatten them into one generic “IB aligned” label.

| Field | Requirement |
|---|---|
| Programme/course/year | MYP / Language and Literature / Year 1 |
| Content ID and version | Stable ID; revision creates a new version |
| Framework/source baseline | Exact source title, publisher, URL, edition/date and scope |
| Source confidence | Current public IB fact; legacy official reference; independent specialist example; research principle; platform design decision; unverified/transition watch |
| Official map state | not_started, source_pending, legacy_crosswalk_only, mapped_pending_review, verified, or general_unmapped |
| Official objective references | Blank until current guide and relevant wording are verified; old A–D notes are stored separately as legacy crosswalk, not current official mapping |
| Enhanced MYP state | not_reviewed, watchlist, official_release_pending, impact_assessed, remapping_required, or verified_for_use |
| Intended outcomes | Learner-readable goal plus internal measurable outcome |
| Skill modes | Listening, speaking, reading, writing, viewing, presenting; record only what the task actually supports |
| Learning design | Model, guided practice, deliberate practice, independent transfer, feedback, revision, reflection |
| Assessment evidence | Task ID, expected response, internal rubric version, teacher/editor guidance location |
| Rights status | original, licensed, permissioned, public-domain verified, or blocked |
| Academic review | not_started, draft, in_review, approved, revisions_required |
| Accessibility review | not_started, in_review, passed, blocked |
| Release status | planned, draft, in_review, approved, published, retired |
| Provenance | Exact source URL, relevant section/page, checked date, reviewer, rights notes and rationale |
| Progression links | Previous/next links and prerequisites only when curriculum logic is reviewed |

A source-review pass does not automatically set official map state to verified. Academic, rights, accessibility and release statuses remain independent.

## 5. Unit-planner template

Use this planner for each of the six units, with current/legacy and Enhanced MYP transition fields shown in separate zones.

### A. Identity and inquiry
- Course and year; unit ID/version; working title; hours; local adaptation notes.
- Driving question and an accessible learner-facing purpose.
- Context/text types and a brief reason the unit matters to learners.
- What knowledge or experience is assumed, and what entry diagnostic will check.
- Student-facing success evidence.

### B. Framework links
- **Current public framework:** link only verified subject aims and relevant current programme elements.
- **Legacy reference:** if helpful, note historical A–D lenses as legacy crosswalk only.
- **Enhanced MYP watchlist:** record beta/future terminology separately with source/version and current status; never treat beta fields as final official mapping.
- ATL/skills and concepts: choose only when they support the unit, and label a platform choice as a choice rather than an official mandate.
- No unverified official codes.

### C. Learning experience sequence
1. Entry diagnostic and misconception check.
2. Explicit instruction and annotated model.
3. Guided practice with prompts and feedback.
4. Deliberate practice with a second example and changing context.
5. Independent transfer on a fresh text/task.
6. Feedback and revision.
7. Exit evidence, reflection and next-step rule.

### D. Task and review pack
- Learner tasks and expected evidence.
- Internal rubric and feedback language.
- Teacher/editor notes, answers and likely misconceptions stored outside the learner-facing bundle.
- Differentiation, accessibility, cultural/context review and rights ledger.
- Reviewer and version history.
- Release/readiness checklist independent of curriculum mapping.

## 6. Target implementation sequence — conditional on guide approval

**No application or Unit 1 work is authorized by this document revision.** Following founder approval, use the sequence below.

1. Reconcile the existing preview with revised Unit 1 outcomes and source controls; do not duplicate it.
2. Record a task-by-task alignment table connecting the preview's learning outcomes, examples, practice tasks and feedback to the revised guide. Treat the legacy A–D labels as a diagnostic crosswalk until currentness is validated.
3. List all text/image/audio assets and verify rights; replace or rewrite any item without clear permission.
4. Audit direct evidence for reading, viewing, writing, speaking/listening and transfer; include any skill that is claimed but not assessed.
5. Revise the lesson and separate teacher/editor review pack only after the founder approves the guide.
6. Complete academic, accessibility, cultural-suitability and rights reviews separately.
7. Keep the pilot in preview until all applicable mapping, rights, accessibility and explicit release gates are passed.
8. After Unit 1 content is complete, present it for founder approval. Do not move to the next curriculum guide before that approval.
9. Only after content approval may authorized application changes be made in a branch/PR, with source metadata, route data, accessibility checks and automated tests.
10. Verify CI and deployment from actual results. Do not infer that a changed document means the app is updated or deployed.

## 7. Enhanced MYP change-control workflow

When the final Enhanced MYP subject guide becomes available:
1. Record the official publication URL, version, publication date, effective/implementation date and any teacher-support document dependencies.
2. Compare the current public framework, legacy 2014/15 guide reference, beta documents and final guidance.
3. Create a detailed field-by-field change log for concepts, planner fields, objective/criteria wording, assessment and reporting.
4. Review every affected Year 1 outcome, unit, task, rubric and route metadata.
5. Keep the prior version and crosswalk in Git history; update the source register and all dependent docs.
6. Obtain founder approval before changing any learner-facing current-mapping claim or task sequence.

A third-party update or beta interface alone must not trigger a claim that a new requirement is final.
